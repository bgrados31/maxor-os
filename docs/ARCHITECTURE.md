# Architecture

Maxor OS is a single flake with one host (`nitro`) and a user configuration managed by
home-manager as a NixOS module. The design rule is to separate four things:

1. **What changes per machine** (disks, GPU, name): `hosts/<host>/`.
2. **What defines Maxor** (name, fonts, boot): `modules/`.
3. **What the user sees and touches** (terminal, shortcuts, lock screen, themes): `home/`.
4. **What the user can change without `rebuild`** (themes): `~/.local/share/maxor/` and
   `~/.config/maxor/`.

## How color responsibilities are split

There is a single source of truth for colors: the active theme.

```
 ~/.local/share/maxor/themes/<theme>/colors.json
                  │
        maxor theme apply
                  │
   ┌──────────────┼───────────────────────┐
   ▼              ▼                       ▼
 dms-theme.json   hyprlock.conf       wallpaper.png
   │              (template +           (dms ipc wallpaper)
   │               palette)
   ▼
 DMS (matugen/templates)
   │
   ├─ bar, launcher, notifications
   ├─ kitty      (~/.config/kitty/dank-theme.conf)
   ├─ Hyprland   (~/.config/hypr/dms/colors.lua)
   └─ GTK / Qt
```

`maxor theme apply` generates a theme of its own for DMS and activates it by editing
`~/.config/DankMaterialShell/settings.json` (`currentThemeName = "custom"`,
`customThemeFile`). DMS takes care of recoloring the rest. The lock screen does not depend on DMS:
`home/lockscreen.nix` publishes a template with markers (`@FG_RGB@`, `@AC_RGB@`, …) that the CLI
fills in with the palette. The full-screen app reads the same active theme and paints its whole
interface with it.

## The CLI and the full-screen app

```
 you ──▶ maxor-tui (Go) ──▶ maxor … --json (bash) ──▶ nix, flatpak, systemd, git
 you ──▶ maxor …        (bash, linear output)      ──▶ the same things
```

The CLI is the only place with logic; the full-screen app reimplements nothing, it calls `maxor`
with `--json` and reads the result. What needs root (applying the system, going back to a
generation) goes through `sudo`; the app asks for the password in its own field and hands it to
`sudo` through standard input (`MAXOR_SUDO_STDIN=1`).

## Desktop session

- **Login:** greetd with the DMS greeter (Maxor Shell package) inside Hyprland; see
  [SHELL.md](SHELL.md). It inherits the user's theme, colors and wallpaper.
- **Hyprland:** installed by `programs.hyprland` (NixOS). home-manager only writes the
  configuration (`configType = "lua"`, `package = null`).
- **DMS:** starts as a systemd user service (`programs.dank-material-shell.systemd`).
- **Lock:** `SUPER + ALT + L` runs `loginctl lock-session`; hypridle receives the signal and
  launches hyprlock with the active theme's configuration. If that configuration does not exist,
  it uses the default (Sakura). hyprlock's PAM is declared in `hosts/nitro/configuration.nix`.

## Boot

```
UEFI → systemd-boot (ESP, /efi) → kernel + initrd (XBOOTLDR, /boot) → Plymouth → greetd (greeter) → Hyprland
```

The 100 MB ESP is shared with Windows (dual boot). Kernels and initrd live on a 1 GB XBOOTLDR
partition mounted at `/boot`, so that NixOS generations do not fill the ESP.
`configurationLimit = 10` limits how many generations are kept.

## Principles

- **Declarative first.** If something can be expressed in Nix, it is not edited by hand.
- **Reversible.** Every system change is a generation; every theme change is undone with
  `maxor theme undo`.
- **Data, not code, in themes.** A theme cannot run anything. See
  [THEMING.md](THEMING.md#security).
- **Separate system and user.** The user customizes in `~/.config/maxor/`; the system updates
  without overwriting anything of theirs.
- **One place for logic.** The CLI; everything else is a face of it.

## Reusing Maxor from another flake

The system modules are exposed as `nixosModules.default` (core, desktop, identity and fonts).
Another flake can import them and add only its hardware:

```nix
{
  inputs.maxor.url = "github:bgrados31/maxor-os";
  # …
  modules = [ maxor.nixosModules.default ./my-machine.nix ];
}
```

The user configuration (`home/`) is not exported as a module yet; it is a pending step of
[phase 2](ROADMAP.md).

## Hyprland configuration in modules

`hyprland.lua` only loads modules, in this order:

1. `maxor.settings`, `maxor.rules`, `maxor.binds`: read-only, they come from this repository.
2. `dms.*`: theme colors, monitors, cursor, rules and **layout** (corners and gaps) managed by DankMaterialShell.
3. `maxor.theme`: the active theme's shape. It goes after DMS on purpose: DMS's layout sets its own corners and gaps, and if this module loaded earlier, DMS would override it.
4. `maxor.user`: **yours**. It is created once from `user.lua.example`, loaded last and never
   modified by the system, so whatever you put there overrides everything above.

Monitors are managed by DMS (`dms.outputs`); that is why there is no `monitors.lua` of our own.
